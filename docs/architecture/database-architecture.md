# PlanMeal v5 — Архитектура базы данных

> Документ для продакт-менеджера. Объясняет что хранится в базе данных,
> как таблицы связаны друг с другом и почему всё устроено именно так.

---

## Что такое Supabase и зачем он нам

Supabase — это облачная база данных плюс готовый сервер авторизации.
Нам не нужно писать backend с нуля: Supabase берёт на себя хранение данных,
вход/регистрацию пользователей и защиту данных.

Внутри Supabase стоит **PostgreSQL** — одна из самых надёжных реляционных баз данных в мире.
Данные хранятся в таблицах (как в Excel), но таблицы связаны между собой.

---

## Что сделал SQL-скрипт

Скрипт выполнил три вещи по порядку:

### 1. Создал таблицы (10 штук)
Это как создать пустые листы в Excel — задать структуру (какие колонки есть),
но данных ещё нет. Все таблицы создавались в схеме `public` (публичная область Supabase).

### 2. Включил защиту (RLS — Row Level Security)
RLS — это система "кто что видит". Без неё любой пользователь мог бы прочитать
данные любого другого. После включения RLS и написания политик каждый пользователь
видит только то, что ему разрешено.

Аналогия: представь Google Docs. Документ существует, но ты видишь только те документы,
к которым у тебя есть доступ. RLS — это та же идея, но на уровне строк в таблице.

### 3. Создал автоматику (триггер `handle_new_user`)
Триггер — это код, который запускается автоматически при каком-то событии.
Наш триггер срабатывает каждый раз когда новый пользователь регистрируется.

Он делает три вещи за пользователя автоматически:
1. Создаёт запись в таблице `profiles` (профиль пользователя)
2. Генерирует уникальный **код приглашения** формата `ABCDE-1X2Y`
3. Создаёт личное **домохозяйство** и привязывает пользователя к нему

То есть сразу после регистрации у пользователя уже есть личное пространство —
он не попадает в "пустоту".

---

## Схема связей между таблицами

```
auth.users (встроенный в Supabase)
    │
    ↓ триггер создаёт автоматически
    │
    ├──→ profiles (профиль)
    │
    ├──→ households (домохозяйство)
    │         │
    └──→ household_members ←──────────────────┐
              │ (связывает users ↔ households) │
              │                               │
              ↓                               │
         personas (члены семьи)               │
              │                          household_join_requests
         menu_plans (меню)               (заявки на вступление)
         custom_dishes (блюда)
         custom_products (продукты)
         household_fridge (холодильник)
```

## Таблица 1 — `profiles`

**Что хранит:** базовую запись о каждом зарегистрированном пользователе.

**Зачем нужна отдельно от auth.users?**
Supabase имеет встроенную таблицу `auth.users` для хранения email и пароля.
Но к ней нельзя добавлять свои колонки и нельзя делать RLS-политики.
Поэтому стандартная практика — создать свою таблицу `profiles`, которая
ссылается на `auth.users` и куда можно добавить любые данные о пользователе.

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | uuid | Тот же ID что и в auth.users. UUID — это уникальный идентификатор вида `a1b2c3d4-...` |
| `created_at` | timestamp | Когда создан профиль |

**Сейчас минималистична** — в будущем сюда можно добавить имя пользователя,
аватар, язык интерфейса и т.д.

---

## Таблица 2 — `households`

**Что хранит:** домохозяйства (семьи/группы пользователей).

**Концепция:** В PlanMeal каждый пользователь принадлежит к домохозяйству.
Это может быть его личное пространство (один человек) или семейное (несколько людей).
Все меню, блюда, корзина — общие для всего домохозяйства.

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | uuid | Уникальный ID домохозяйства |
| `invite_code` | text | Код приглашения формата `ABCDE-1X2Y`. По нему другие люди могут попроситься в эту семью |
| `created_at` | timestamp | Когда создано |

**Пример:** Маша регистрируется → триггер создаёт домохозяйство `id=abc123`,
с кодом `GRAPE-7X2K`. Если Маша хочет добавить мужа — она даёт ему этот код.

## Таблица 3 — `household_members` ⭐ Ключевая таблица

**Что хранит:** связь между пользователем и домохозяйством.

Это самая важная таблица с архитектурной точки зрения. Здесь решается
кто к какой семье сейчас принадлежит.

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | uuid | ID записи |
| `user_id` | uuid | Кто этот пользователь (→ profiles) |
| `household_id` | uuid | В каком домохозяйстве он **сейчас активен** |
| `own_household_id` | uuid | Его **личное** домохозяйство (создано при регистрации, **никогда не меняется**) |
| `joined_at` | timestamp | Когда вступил |

### Ключевая логика: два разных household_id

Это решение придумано чтобы правильно обрабатывать ситуацию "вступил в семью и вышел":

```
При регистрации:
  household_id     = abc123  ← личная семья
  own_household_id = abc123  ← тоже личная

После вступления в семью жены (def456):
  household_id     = def456  ← теперь активна семья жены
  own_household_id = abc123  ← личная ОСТАЛАСЬ прежней

После выхода из семьи жены:
  household_id     = abc123  ← вернулся в свою
  own_household_id = abc123  ← не менялась
```

**Как определить роль пользователя:**
- `household_id === own_household_id` → **Владелец** (он в своей семье)
- `household_id !== own_household_id` → **Гость** (он в чужой семье)

Это позволяет не хранить отдельную колонку "роль" — роль вычисляется автоматически.

## Таблица 4 — `personas`

**Что хранит:** профили членов семьи с их физическими параметрами и целями по питанию.

Важно: **пользователь ≠ персона**. Пользователь — это аккаунт (email + пароль).
Персона — это "кто ест" с биопараметрами (пол, вес, рост) и нормами КБЖУ.

**Два типа персон:**

**Auth-персона** — у живого пользователя с аккаунтом. `user_id` заполнен.
> Пример: Маша зарегистрировалась → у неё есть auth-персона "Маша"

**Локальная персона** — для члена семьи без аккаунта. `user_id = NULL`.
> Пример: Маша создала персону "Дочка Аня 7 лет" — у Ани нет аккаунта,
> но её меню и КБЖУ учитываются

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | bigint | Числовой ID персоны |
| `household_id` | uuid | К какому домохозяйству принадлежит |
| `user_id` | uuid или NULL | Если NULL — локальная персона |
| `created_by_user_id` | uuid или NULL | Кто создал эту персону (важно для прав доступа) |
| `name` | text | Имя персоны ("Маша", "Дочка Аня") |
| `gender` | text | `male` или `female` |
| `age` | int | Возраст в годах |
| `weight` | decimal | Вес в кг |
| `height` | decimal | Рост в см |
| `activity` | text | Уровень активности: `sedentary` (сидячий) → `very_active` (очень активный) |
| `formula` | text | Формула расчёта КБЖУ: `mifflin` или `harris` |
| `kcal_target` | int | Норма калорий в день |
| `protein_target` | int | Норма белков (г) |
| `fat_target` | int | Норма жиров (г) |
| `carbs_target` | int | Норма углеводов (г) |
| `meal_ratios` | jsonb | **Новое в v5!** Распределение по приёмам пищи: `{"bf":25,"ln":40,"dn":35}` (% от суточной нормы) |

**Почему `meal_ratios` в базе, а не в localStorage как в v4?**
В v4 эти проценты хранились только в браузере — при входе с другого устройства
они сбрасывались. Теперь настройки сохраняются в базе и доступны везде.

## Таблица 5 — `menu_plans`

**Что хранит:** план питания — одна строка на одно блюдо в слоте.

Одна строка = одно блюдо в конкретном приёме пищи конкретного дня конкретной недели персоны.
В одном приёме пищи может быть несколько блюд (несколько строк с одинаковыми persona_id + week_label + day_index + meal_key).

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | bigint | ID записи |
| `persona_id` | bigint | Чей план |
| `week_label` | text | Номер недели в формате `2026-W14` |
| `day_index` | int | День недели: 0=пн, 1=вт, ... 6=вс |
| `meal_key` | text | Приём пищи: `bf` (завтрак), `ln` (обед), `dn` (ужин), `sn` (перекус) |
| `dish_name` | text | Название блюда |
| `dish_photo` | text | URL фото блюда |
| `dish_category` | text | Категория: breakfast / main / side / salad / snack |
| `kcal` | int | Калории в этой порции |
| `protein` | int | Белки (г) |
| `fat` | int | Жиры (г) |
| `carbs` | int | Углеводы (г) |
| `cost` | int | Стоимость порции (₽) |
| `grams` | int | Вес порции (г) |
| `sort_order` | int | Порядок блюд внутри одного приёма пищи |
| `created_at` | timestamp | Когда создана запись |

**Индекс:** на `(persona_id, week_label)` — ускоряет загрузку меню персоны на неделю.

## Таблица 6 — `custom_dishes`

**Что хранит:** кастомные блюда, созданные пользователями домохозяйства.

Приложение имеет встроенный список блюд (в коде). Но пользователи могут добавлять
свои. Они хранятся здесь.

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | bigint | ID записи |
| `household_id` | uuid | Чьё блюдо (видят все члены домохозяйства) |
| `data` | jsonb | Всё о блюде одним объектом |
| `created_at` | timestamp | Когда добавлено |

**Структура `data`:**
```json
{
  "id": "cd_1234567890",
  "name": "Борщ бабушки",
  "cat": "dinner",
  "cost": 150,
  "kbju": { "k": 280, "p": 12, "f": 8, "c": 35 },
  "ing": [
    { "k": "свёкла", "a": 200, "u": "г" },
    { "k": "капуста", "a": 150, "u": "г" }
  ],
  "photoUrl": "https://...",
  "source": "custom"
}
```

Важно: `cost` и `ing[].a` — значения **на 1 персону**.
При отображении для 3 человек умножаем на 3.

## Таблица 7 — `custom_products`

**Что хранит:** кастомные продукты — расширение встроенного справочника продуктов.

Встроенный справочник содержит базовые продукты (молоко, яйца и т.д.).
Если пользователю нужен специфический продукт — он добавляет его сюда.

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | bigint | ID |
| `household_id` | uuid | Чей продукт |
| `data` | jsonb | Всё о продукте |

**Структура `data`:**
```json
{
  "key": "custom_молоко_безлактозное",
  "name": "Молоко безлактозное",
  "type": "pkg",
  "pkgSize": 1,
  "pkgUnit": "л",
  "defPrice": 120
}
```

Типы продуктов: `pkg` (упаковка), `wgt` (весовой/на граммы), `pcs` (поштучный).

## Таблица 8 — `household_fridge`

**Что хранит:** содержимое холодильника домохозяйства.

Одна строка на продукт (row-per-item). Если Маша и Петя в одной семье — у них один общий холодильник.

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | bigint | ID строки (GENERATED ALWAYS AS IDENTITY) |
| `household_id` | uuid | ID домохозяйства |
| `product_name` | text | Название продукта |
| `qty` | numeric | Количество |
| `unit` | text | Единица: `г`, `кг`, `мл`, `л`, `шт` |
| `expires_at` | timestamp | Срок годности (необязательно) |
| `created_at` | timestamp | Когда добавлен |
| `updated_at` | timestamp | Когда последний раз изменён |

**Особенности:**
- Предупреждение если `expires_at` уже прошёл (красный) или ≤ 3 дней (жёлтый)
- При формировании корзины product_name сравнивается с ингредиентами блюд (case-insensitive)
- Совпавшие продукты вычитаются из итога корзины

## Таблица 9 — `menu_templates`

**Что хранит:** сохранённые шаблоны меню на уровне домохозяйства.

Пользователь может сохранить текущую неделю как шаблон и применить его к любой другой неделе.

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | bigint | ID шаблона |
| `household_id` | uuid | Шаблон виден всем членам домохозяйства |
| `created_by` | uuid | Кто создал (только создатель может удалить) |
| `name` | text | Название шаблона (вводит пользователь, до 60 символов) |
| `slots` | jsonb | Массив слотов блюд (day_index, meal_key, dish_name, КБЖУ, grams и т.д.) |
| `created_at` | timestamp | Когда создан |

**RLS:** SELECT/INSERT — любой член домохозяйства; DELETE — только `created_by = auth.uid()`.

## Таблица 10 — `household_join_requests`

**Что хранит:** заявки на вступление в семью.

**Зачем не просто "вступить по коду"?**
Прямое вступление по коду — дыра безопасности: можно перебирать коды и
вламываться в чужие семьи. Поэтому реализован двухшаговый процесс:
1. Пользователь подаёт заявку (вводит код)
2. Владелец семьи видит заявку и одобряет или отклоняет

| Колонка | Тип | Описание |
|---------|-----|---------|
| `id` | uuid | ID заявки |
| `household_id` | uuid | В какую семью хотят вступить |
| `requester_user_id` | uuid | Кто подал заявку |
| `requester_name` | text | Имя заявителя (чтобы владелец понял кто это) |
| `status` | text | `pending` (ожидает) → `approved` (принята) или `rejected` (отклонена) |
| `created_at` | timestamp | Когда подана |

## Политики безопасности (RLS) — как работает защита

RLS — это правила "кто что видит и меняет". Записываются в виде условий на SQL.

**Принцип для всех таблиц:**

```
Пользователь видит только то, что принадлежит его домохозяйству.
```

Это реализовано через подзапрос:
```sql
household_id IN (
  SELECT household_id FROM household_members WHERE user_id = auth.uid()
)
```
Здесь `auth.uid()` — это функция Supabase, которая возвращает ID текущего пользователя.
То есть каждый запрос автоматически фильтруется по пользователю — без кода на фронтенде.

**Особые случаи:**

| Таблица | Кто может изменять |
|---------|-------------------|
| `personas` | Свою auth-персону — только сам. Локальную — только создатель |
| `household_join_requests` | Видит заявку: либо сам заявитель, либо владелец семьи |
| `households` | Обновлять (менять invite_code) может только владелец |

## Итоговая схема одним взглядом

```
Регистрация пользователя
    ↓ (автоматически через триггер)
profiles + households + household_members
    ↓
Онбординг: пользователь создаёт персону
    ↓
personas (с kcal_target, meal_ratios и т.д.)
    ↓
Планирование меню
    ↓
menu_plans (plan_data: {mon_bf: 5, mon_ln: 12, ...})
    ↓
Корзина (вычисляется на лету из menu_plans)
    ↓
Вычитание того что есть дома
    ↓
household_fridge
```

| Что | v4 | v5 |
|-----|----|----|
| `meal_ratios` (bf/ln/dn %) | В localStorage браузера | В базе данных (`personas.meal_ratios`) |
| Индекс на `menu_plans` | Нет | Есть (`persona_id, week_label`) |
| Триггер `handle_new_user` | Иногда падал (проблема с FK) | Исправлен, правильный порядок INSERT |
| Совместимость с v4 данными | — | Нет (новая база, миграция не нужна) |
